# 企业级业务规则梳理指南 (Business Rules Modeling)

在企业级应用（如 ERP、CRM、考勤报工、供应链、财务结算）中，**业务规则 (Business Rules)** 是 PRD 最核心的灵魂资产。

如果业务规则与交互细节或功能入口杂糅，将导致规则碎片化、逻辑冲突以及开发漏测。本指南规定了业务规则的识别、抽象、解耦与编排标准。

---

## 一、什么是真正的业务规则？

国际业务规则工作组 (Business Rules Group) 的经典定义：
> **业务规则是关于业务运作方式的声明，它断言业务的结构，或者控制、约束业务的行为。**

### 核心特征：
1. **独立于用户交互 (UI-Independent)**:
   - 无论用户是在 Web 浏览器、手机 App、API 批量导入，还是由后台定时任务调用，该规则**必须同等生效**。
   - ❌ "当输入超过24时，输入框变红且提交按钮置灰"（这是交互设计表现，非业务规则）。
   - ✅ "任何来源提交的单人单日工时总量，严禁超过24.0小时"（这是纯粹的业务规则）。
2. **独立于技术实现 (Tech-Independent)**:
   - 规则不依赖特定的数据库触发器、ORM 验证器或前端校验框架。
   - ❌ "在 PostgreSQL 使用 CHECK (hours <= 24) 约束"。
3. **原子性与声明性 (Declarative & Atomic)**:
   - 规则应描述“必须是什么”或“禁止是什么”，而非“先执行函数A再执行函数B”。

## 二、业务规则四大原型分类 (The 4 Archetypes)

### 1. 约束性规则 (Constraint Rules)
设定业务数据或行为的硬性上限、下限、唯一性或互斥条件。
- **典型场景**: 数值界限、时间跨度、唯一标识、排他性。
- **示例**:
  - `BR-CON-01`: "单次请假最小时长为0.5个工作日，最大单次不得超过15个工作日。"
  - `BR-CON-02`: "同一员工在同一时间段内仅允许存在一条生效的项目归属记录。"

### 2. 计算与衍生规则 (Derivation & Calculation Rules)
定义业务数据的派生逻辑、汇总方式、换算比率或计算公式。
- **典型场景**: 薪酬计算、工时折算、税费测算、信用分评级。
- **示例**:
  - `BR-CAL-01`: "标准工时折算公式: `有效人天 = 实际工时 ÷ 8.0`，保留两位小数，采用四舍五入法则。"
  - `BR-CAL-02`: "夜班津贴系数：在 22:00 至次日 06:00 期间产生的工时，按 1.5 倍基准系数结算。"

### 3. 时效与时序规则 (Temporal & Lifecycle Rules)
规定事件发生的先后顺序、生效时间窗口、冻结期或追溯期。
- **典型场景**: 补录时限、反结账期限、审批超时、数据留存归档。
- **示例**:
  - `BR-TIME-01`: "补录窗口限制：每月报工补录仅允许在次月的前 3 个工作日内完成，逾期系统自动关闭补录入口。"
  - `BR-TIME-02`: "已归档的历史月度报工数据永久进入只读状态，任何角色均无权直接变更。"

### 4. 准入与策略规则 (Eligibility & Policy Rules)
定义操作或享受某项权益的资格门槛与前置准入条件。
- **典型场景**: 权限准入、白名单政策、风控评级。
- **示例**:
  - `BR-POL-01`: "外包服务人员仅在服务合同处于有效（Active）状态下，才具备工时录入资格。"

## 三、业务规则在 PRD 中的标准描述模板

在 `templates/prd-template.md` 第 6 节中，每一条被编译出的业务规则均须具备以下结构要素：

```markdown
### BR-01: [规则名称，简洁精练]
- **规则定义**: [清晰阐明规则的业务约束逻辑、计算公式或界限，使用确定性陈述]
- **适用场景**: [在哪些模块、业务阶段或特定用户群组中生效]
- **前置条件**: [规则触发或评估所依赖的上下文]
- **违规处理 / 提示**: [当业务操作触犯该规则时，系统应给予的业务级反馈与应对策略]
- **溯源引用**: [对应 spec.md 中的 Requirement 编号或 Scenario 来源]
```

### 范例演示：
```markdown
### BR-01: 单日累计工时上限约束
- **规则定义**: 任何员工在单个自然日（00:00:00 至 23:59:59）内跨所有项目申报的有效工作时长总和不得超过 24.0 小时。
- **适用场景**: 员工提交日报、周报汇总以及管理员代表员工代报工时。
- **前置条件**: 报工日期已选定，且已有该日期历史记录存在或本次填报包含该日期。
- **违规处理**: 阻止操作，反馈明确业务提示：“单日累计工时已达 X 小时，本次填报 Y 小时将超出单日 24 小时法定上限，请重新核实”。
- **溯源引用**: `spec.md#FR-002`
```

## 四、常见反模式与质量自查

| 常见反模式 (Bad Smell) | 危害 | 正确做法 |
|:---|:---|:---|
| **将校验混入功能介绍**<br/>"功能：支持员工输入工时，前端需校验不能大于24" | 漏掉批量导入、后台接口对该规则的约束 | 剥离出独立的 `BR-01`，功能介绍只讲“员工可输入并提交每日工时” |
| **规则包含具体技术栈**<br/>"后端在拦截器中调用 Redis 判断计数" | 约束了架构方案，非技术人员读不懂 | 描述纯业务逻辑，技术实现由开发团队在 `plan.md` 中决定 |
| **规则含义模糊，留有推诿空间**<br/>"工时不可过长，历史记录及时提交" | 无法编写确定性验收测试用例 | 明确量化为具体数字与截止期限（若未知，标记 `[NEEDS CLARIFICATION]`） |
| **违规处理写成 HTTP 状态码**<br/>"违规返回 HTTP 400 Bad Request" | 破坏产品层视角 | 描述业务层提示信息与阻断策略 |
