# PRD 核心设计哲学与生成原则 (PRD Principles)

本指南阐述 `spec-kit-prd` 扩展的核心设计哲学与基本原则。所有参与生成、审阅与维护 PRD 的命令及 Agent 行为均须严格遵循此原则。

---

## 一、核心定位：从“事实源”到“产品视角编译器” (PRD Compiler)

### 1. 唯一事实源原则 (Single Source of Truth)
```text
                  用户诉求 / 业务需求
                           │
                           ▼
                   /speckit.specify
                           │
                           ▼
                ┌─────────────────────┐
                │       spec.md       │ ◄── 唯一事实源 (Single Source of Truth)
                └─────────────────────┘
                    │             │
        (编译投影)  │             │ (工程拆解)
                    ▼             ▼
       ┌─────────────────┐   ┌─────────────────┐
       │ product/prd.md  │   │     plan.md     │
       │ (Stakeholder)   │   │ (Architecture)  │
       └─────────────────┘   └─────────────────┘
```

- **`spec.md` 是且仅是规范驱动开发 (SDD) 中的唯一事实源 (Canonical Source of Truth)**。
- **PRD Extension 是一个只读的“产品视角编译器 (PRD Compiler)”**，其职责是将 `spec.md` 中面向工程规约的需求陈述，编译重构成适合产品经理、业务方、运营以及设计团队理解和核对的“产品需求视图 (Product View)”。
- **严禁双向流动 (PRD ─X→ spec.md)**：
  - PRD 永远不允许反向修改或覆盖 `spec.md`。
  - 如果在审阅 PRD 时发现需求缺失或业务逻辑漏洞，**必须回到 `spec.md`**（通过 `/speckit.clarify` 或手动修订），随后重新运行 `/speckit.prd.generate`。
  - 允许双向流动必然导致“双文档事实源漂移 (Dual Document Drift)”，彻底摧毁规范的一致性。

---

## 二、纯粹性原则：WHAT & WHY，严禁 HOW 泄漏

在传统敏捷开发中，PRD 经常沦为架构图、数据库字段设计、API 调用链甚至伪代码的杂糅体。这不仅降低了非技术利益相关者的可读性，更剥夺了工程团队的架构自由度。

### 1. WHAT (做什么) 与 WHY (为什么做)
- **WHY**: 业务背景、用户核心痛点、商业价值、衡量指标、急迫性。
- **WHAT**: 用户能获得的端到端业务能力、系统必须遵守的业务准则与边界约束。

### 2. 严禁 HOW (怎么实现) 泄漏
PRD 编译过程中，**必须主动剥离任何工程实现细节**：
- ❌ **禁止包含技术选型**: 如 "使用 Redis 缓存报工记录"、"基于 Kafka 发送通知"、"使用 Spring Boot 拦截器"。
- ❌ **禁止包含存储/数据库细节**: 如 "在 `t_work_order` 表中新增 `is_deleted` 字段"、"联合索引 (user_id, report_date)"。
- ❌ **禁止包含通信协议与报文细节**: 如 "POST /api/v1/reports 返回 403 Forbidden"、"JSON Payload 格式"。
- ❌ **禁止包含代码架构与类结构**: 如 "定义 WorkReportManager 接口与工厂模式"。

> **例外情况**：若 `spec.md` 明确声明了不可变更的**业务外部系统集成契约**（例如“需符合税务局国税发票格式 GB/T-xxxx”），这属于业务域约束而非内部技术实现，可归入“11. 风险、依赖与约束”。

## 三、语义升维：重构需求语义，而非简单摘要文本

`spec-kit-prd` 绝非调用大模型对 `spec.md` 做“缩写”或“格式重排”。它的核心智能在于**需求语义升维 (Semantic Classification & Elevation)**：

1. **三层核心分离 (Three-Tier Separation)**：
   - **功能需求 (Functional Capability)**: 用户能够调用的能力（如：查看本月报工历史）。
   - **业务规则 (Business Rules)**: 业务不变量与硬性约束（如：历史超过30天的记录禁止修改）。
   - **验收标准 (Acceptance Criteria)**: 具体且可穷尽的行为验证用例（Given-When-Then）。
2. **拒绝平铺堆砌**：
   - 避免将业务规则（“一天最多填报24小时”）直接作为功能点平铺。
   - 避免把校验规则混杂在 UI 交互流程中描述。

## 四、真实保真原则：严禁幻觉脑补与透传待确认项

### 1. 零幻觉 (Zero Hallucination)
- PRD 编译器严禁为了使文档“看起来更丰富”而凭空捏造未在 `spec.md` 中提及的业务流程、附加功能或非事实假定。
- 若背景信息在 `spec.md` 中较为精简，应基于 `spec.md` 的现有上下文提炼其核心目标，严禁凭空扩写未确认的业务范围。

### 2. `[NEEDS CLARIFICATION]` 原样上浮透传
- `spec.md` 中未敲定的待澄清事项（标注有 `[NEEDS CLARIFICATION: ...]` 或类似标记的内容），是工程与产品对齐的关键分歧点。
- **严禁 AI 在生成 PRD 时自行扮演“业务专家”回答这些问题！**
- 编译器必须将每一个待澄清事项提取并原样呈现在 PRD 的 **第 12 节【待确认事项】** 中，明确标注影响范围与待决策状态。

---

## 五、受众共情与可读性审查 (The Reader Test)

借鉴 Anthropic `doc-coauthoring` 的优秀经验，PRD 生成后须通过“读者测试 (Reader Test)”：
1. **利益相关者同理心**:
   - 业务方能否在 3 分钟内通读第 1 节到第 4 节并理解范围与价值？
   - QA 团队能否直接依据第 10 节验收标准派生出测试用例？
   - 研发架构师能否在不被 PRD 限制技术细节的前提下，依据第 5、6、7、8 节准确理解业务约束？
2. **结构清晰与视觉层次**:
   - 善用 Markdown 表格呈现字段、角色权限与追溯矩阵。
   - 编号体系保持连贯（FR-xx, BR-xx, AC-xx, OQ-xx）。
3. **全链路可追溯性 (Bidirectional Traceability)**:
   - PRD 末尾必须输出规范追溯矩阵（Section 13），确保每一条功能与规则都能找到出处，未有任何遗漏。
